# 宝塔面板真实IP自动修复脚本

> 适用环境：宝塔面板 11.x + 反向代理环境（如面板域名经 CDN 等代理层回源）

当宝塔面板经反向代理（如 CDN）回源时，面板登录日志、IP 白名单、封禁等功能只能看到**上一层代理的 IP**，而看不到真实客户端 IP。本脚本自动修复这个问题，并在面板升级覆盖后一键恢复。

## 问题根因

- 宝塔 **PHP 网站**由 Nginx 提供，开启「CDN IP 识别」后靠 Nginx 的 `real_ip` 模块把 `X-Forwarded-For` 里的真实 IP 重写进 `$remote_addr`，所以网站能拿到真实 IP。
- 宝塔 **面板本体**是一个独立的 Python/Flask 服务，取 IP 靠 `/www/server/panel/class/public.py` 里的 `GetClientIp()`，默认只取 `request.remote_addr`（即 TCP 对端 = 上一层代理的 IP），并不解析 `X-Forwarded-For`。

面板侧其实有**两个坑，只修第一个是不够的**：

### 坑 1 · 取错了 X-Forwarded-For 的位置

11.x 的 `GetClientIp()` 已有「本地代理信任」逻辑：当 `remote_addr` 为 `127.0.0.1` 时读取 `X-Forwarded-For`，但原版取的是 `forwarded_ips[-1]`（最后一个 = 上一层代理的 IP）。叠加 CDN 等代理层后，真实客户端 IP 其实是 `forwarded_ips[0]`（最左边）。

### 坑 2 · 信任条件太窄，XFF 分支根本不执行（v2 解决的重点）

原判断是：

```python
if ipaddr in ('127.0.0.1', '::1', "localhost"):
```

**只有反代用 `127.0.0.1` 连面板时才成立。** 若反代是用「本机内网 IP」（如 `192.168.x.x`）或「容器网关 IP」（如 `172.17.0.1`）连面板，该判断为假，读 `X-Forwarded-For` 的整段分支被直接跳过 —— 此时**即使把 `[-1]` 改成 `[0]` 也完全无效**，面板会一直显示反代机器自己的 IP。

> 典型症状：脚本执行成功、grep 也能搜到 `forwarded_ips[0]`，但面板登录 IP 依然是个内网地址。

## 修复方式

| 坑 | 修法 |
|---|---|
| 坑 1 · 取错 XFF 位置 | `forwarded_ips[-1]` → `forwarded_ips[0]`（取最左 = 真实客户端 IP） |
| 坑 2 · 信任条件太窄 | `ipaddr in ('127.0.0.1', ...)` → **回环 + 私有网段**（覆盖同机内网 IP、容器网关、跨机反代） |

> **只做第 1 件事（v1）在跨机反代场景下是不够的** —— 信任条件没放宽，XFF 分支压根不执行。
> 实测（反代走内网 IP：`XFF=<真实公网IP>, 192.168.x.x`，`remote_addr=192.168.x.x`）：
> 原版与只改 `[-1]→[0]` 的版本都返回 `192.168.x.x`，只有放宽信任条件后才返回真实公网 IP。

### 排查提示 · 若 XFF 里根本没有真实 IP（要在反代侧解决，改面板代码无效）

有些链路里，中间某层反代没有「追加」上游的 XFF，而是用自己的 `$remote_addr` 把整个头**重写**了：

```nginx
# 错误写法：覆盖 —— 真实IP就此丢失
proxy_set_header X-Forwarded-For $remote_addr;
# 正确写法：追加 —— 保留最左边的真实客户端IP
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

典型症状（用 PHP 探针确认，见后文验证章节）：

```
X-Forwarded-For: 192.168.x.x, 192.168.x.x   <- 真实IP已丢失，只剩内网IP重复
Eo-Client-Ip:    <真实公网IP>                <- 真实IP其实还在这儿
```

**注意**：某些反代工具带「自动透传 / 一键优化」类的总开关，它会**强制用 `remote_addr` 覆盖**，
把你手动指定的真实 IP 来源头（如 `Eo-Client-Ip`）冲掉。
遇到这种情况，**关掉那个总开关**即可 —— 数据源本身已被污染，改面板代码是没用的。

## 脚本功能

### `bt_panel_realip_patch.sh`（修补脚本，v2）

- **自动检测**：检查 `public.py` 是否已应用 v2 增强（特征变量 `_bt_ipaddr_trusted`）。
- **自动修补**：
  - 把信任条件从「仅 `127.0.0.1`」放宽为「回环 **+** 私有网段」，让 XFF 分支真正执行；
  - 兼容处理 `forwarded_ips[-1]` → `forwarded_ips[0]`。
  - 用 Python 正则按函数体定位，**只改 `GetClientIp()` 内部**，不误伤其它代码。
- **公网直连防伪造**：公网来源不被信任，其自带的 XFF 会被忽略。
- **自动备份**：修补前把原文件备份到 `/root/bt_patch_backup/`。
- **校验 + 重载**：`py_compile` 语法检查通过后再 `bt restart`。
- **结构变化会报警**：找不到 `GetClientIp()` 或信任判断语句时**报错退出**而非静默跳过，避免"以为修好了其实没修"。
- **幂等 & 静默**：已修复时直接静默退出、不写日志，适合放定时任务每天跑。

### `bt_realip_diagnose.sh`（诊断脚本，只读）

当「脚本跑了、计划任务显示 Successful，但 IP 还是不对」时用它定位。**只读采集，不修改任何文件**：

- 宝塔版本与面板端口、面板进程启动时间（确认补丁后是否真的重启过）
- `GetClientIp()` 当前完整源码
- `forwarded_ips[-1]` / `[0]` 特征、以及 v2 增强是否已应用
- **面板端口的实际来源 IP** —— 判断 `remote_addr` 是不是 `127.0.0.1`，用来区分上面两个坑
- **抓包看面板实际收到的 `X-Forwarded-For`** —— 确认反代有没有把真实 IP 透传过来（补丁生效的前提）
- 面板登录日志、locale 状态

```bash
bash bt_realip_diagnose.sh
```

> 跑之前**先在浏览器刷新一下面板页面**，否则可能抓不到活跃连接，`[4]` 段会是空的。

## 使用方法

### 1. 手动运行（立即修复）

```bash
# 把脚本传到服务器后：
chmod +x bt_panel_realip_patch.sh
bash bt_panel_realip_patch.sh
```

### 2. 配置定时任务（应对面板升级覆盖）

面板升级 / 修复会覆盖 `public.py`，把 v2 的增强一并抹掉。用定时任务每天自动检测并恢复：

**方式 A：宝塔面板自带「计划任务」（推荐）**

1. 宝塔面板 → 计划任务 → 添加任务
2. 任务类型：**Shell 脚本**
3. 执行周期：**每天**，时间选凌晨（如 04:00）
4. 脚本内容：`bash /root/bt_panel_realip_patch.sh`
5. 保存后点「执行」可立即验证一次

**方式 B：系统 crontab**

```bash
crontab -e
# 加入：
0 4 * * * bash /root/bt_panel_realip_patch.sh >> /var/log/bt_realip_patch.log 2>&1
```

> 日志位于 `/var/log/bt_realip_patch.log`。已修复的日子里脚本静默退出、不产生任何日志；只有在真正打补丁（如升级后）时才会记录。

### 3. 验证是否真的生效

**别只看计划任务的 `Successful`** —— 那只是"脚本退出码为 0"，不代表补丁生效。按顺序确认：

**① 先搞清楚真实 IP 藏在哪个头里（最关键的前提）**

放一个简单的 PHP 探针到能被反代访问到的站点，把所有请求头打出来：

```php
<?php
header('Content-Type: text/plain; charset=utf-8');  // 不加这行, 浏览器会把换行折叠成一行
print_r(getallheaders());
?>
```

重点对比 `REMOTE_ADDR`、`X-Forwarded-For`、`X-Real-IP`，以及 CDN 私有头（如 `Eo-Client-Ip`）。
若 `X-Forwarded-For` 里全是内网 IP、真实 IP 只出现在 CDN 私有头里 —— 说明反代把 XFF 覆盖了，
**去反代侧解决**（见上文排查提示），改面板代码无效。

**② 代码有没有改对**

```bash
grep -n "_bt_ipaddr_trusted" /www/server/panel/class/public.py
```

有输出 = v2 已应用。

**③ 面板实际看到的是什么来源 IP**（区分坑 1 / 坑 2）

```bash
ss -tnp | grep ":<面板端口>"
```

- 来源 `127.0.0.1` → 反代走回环，改 `[-1]→[0]` 就够
- 来源 `192.168.x.x` / `172.17.x.x` 等内网地址 → 跨机或容器反代，**必须靠 v2 的私有网段信任**才会生效

**④ 最终确认**

**退出面板重新登录**（面板会缓存会话，不重登看不到变化），再看登录日志里记录的 IP 是否已变成你的真实公网 IP。

## 注意事项

1. **面板升级会覆盖补丁**：这是改核心代码，每次升级后需重打，本脚本即为此设计。
2. **安全风险**：脚本只信任**回环与私有网段**来源 —— 来自公网的直连不会被信任，其 `X-Forwarded-For` 会被忽略，因此公网伪造 XFF 无效。但仍建议**面板端口不对公网裸露**、只允许可信反代链路访问；内网其它机器若也能连到面板端口，理论上可伪造 XFF，有条件的用防火墙把面板端口限定为仅反代机可访问。
3. **IPv6 归属地**：修补后面板能正确显示真实 IPv6 地址，但**地区（省/市）查不到**——这是宝塔内置纯真 IP 库（`qqwry.dat`，IPv4 库）对 IPv6 几乎无覆盖所致，属数据库限制，非配置问题。若需地区显示，可让面板访问域名仅解析 IPv4（去掉 AAAA 记录）。
4. **SSH 登录通知的 IP**：宝塔 SSH 登录微信通知读的是服务器 sshd 日志里的来源 IP。若你用的是面板内「SSH 终端」，sshd 看到的是本机回环，通知只能是内网 IP（Web 终端固有限制）；若用真实 SSH 客户端但走了反向代理端口转发，sshd 看到的是转发器的内网 IP。此问题不在本脚本修复范围内，需另行处理（如 SSH 端口直连公网并加强安全）。
